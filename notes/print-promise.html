Your page says "prints on two pages". Nothing is testing that.

Engineering note · 25 November 2026 · 5 min read

Our site prints things. Every page of weekly planners carries this sentence, in the copy, where the reader sees it before they hit Ctrl-P:

Two printed pages: the week on one, the grocery list on the other.

I had written that sentence, shipped it, and never once printed the page. The day I finally did, it came out as five. The screen layout's generous spacing walked straight into the print stylesheet, every card kept its margin, and the thing I had promised a parent standing at a printer was simply untrue.

What stung was not the CSS. It was that thousands of passing automated checks had no opinion about it, because a sentence in your copy is a claim, and claims need tests. Here is the test, and the two things it taught me that I had wrong.

1. Chrome will print to PDF from the command line, and that is almost enough

Headless Chrome prints a page to a file with no dependencies at all:

"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --no-pdf-header-footer \
  --virtual-time-budget=5000 \
  --print-to-pdf=/tmp/out.pdf "file:///path/to/page.html"

You then need the page count, and you don't need a PDF library for that. The page tree in a PDF carries its own total, so the bytes will tell you:

function pdfPages(buf) {
  const m = /\/Count\s+(\d+)/.exec(buf.toString('latin1'));
  return m ? Number(m[1]) : -1;
}

Twelve printables, a loop, ok(n === 2, ...), and a non-zero exit code. That is the whole guard, and it has sat in our gate ever since. --no-pdf-header-footer matters: without it Chrome adds its own header and footer, which can be the difference between two pages and three. --virtual-time-budget gives webfonts and any client-side rendering a chance to settle before the snapshot — print the page too early and you measure a layout nobody will ever see.

2. --print-to-pdf has no paper flag, so you have only tested one country's paper

This is the part I want to hand to anyone else who ships a printable. There is no --paper-size. The flag prints US Letter, and that is that.

A4 is not a rounding error away from Letter. It is 0.23in narrower and 0.69in taller. Each difference breaks a different thing:

  • Narrower clips. A table that fits Letter's printable width can have its last column sliced off the right edge of an A4 sheet. The page count stays at two. The promise stays "true". The reader loses the quantities column.
  • Taller hides. Content that spills to a third Letter page can fit on two A4 pages, so a Letter-only test can also fail to reproduce a real overflow on the paper most of the world owns.

The DevTools protocol has the knob the command line doesn't: Page.printToPDF takes paperWidth and paperHeight in inches. You can speak it over a WebSocket with no npm install, because Node has a global WebSocket now:

const { cdp } = require('./chrome-cdp.js');   // ~80 lines, spawns Chrome, opens the socket

const A4 = { w: 8.27, h: 11.69 }, MARGIN = 0.4;

const br = await cdp();
const { targetId } = await br.send('Target.createTarget', { url: 'about:blank' });
const { sessionId } = await br.send('Target.attachToTarget', { targetId, flatten: true });
const S = (m, p) => br.send(m, p, sessionId);

await S('Page.enable');
await S('Page.navigate', { url: 'file://' + page });
const pdf = await S('Page.printToPDF', {
  paperWidth: A4.w, paperHeight: A4.h, printBackground: true,
  marginTop: MARGIN, marginBottom: MARGIN, marginLeft: MARGIN, marginRight: MARGIN
});
const n = pdfPages(Buffer.from(pdf.data, 'base64'));

And a page count cannot see sideways clipping, so measure that separately — in print media, at A4's printable width in CSS pixels:

const A4_PX = Math.round((A4.w - 2 * MARGIN) * 96);   // 717px at 96dpi

await S('Emulation.setEmulatedMedia', { media: 'print' });
await S('Emulation.setDeviceMetricsOverride',
        { width: A4_PX, height: 1000, deviceScaleFactor: 1, mobile: false });

…then walk the visible elements and assert that nothing's getBoundingClientRect().right exceeds the viewport. Emulation.setEmulatedMedia is the line that makes this honest: without it you are measuring the screen stylesheet and your @media print rules are not even loaded.

Two practical notes from running this a few hundred times:

  • Page.printToPDF sometimes answers "Printing failed" when the previous print is still winding down. One retry after a short sleep fixed it permanently. A gate that goes red for a reason that isn't about your page is worse than no gate, because you start ignoring it.
  • Give each browser a random debugging port and a fresh --user-data-dir. Two gate steps running at once on a fixed port will attach to each other's browser, and that failure is deeply confusing.

Result on our side: all twelve printables land on the count they promise — two pages each, except one deliberately longer two-week plan that says four on the page — with zero overflow, on both papers. The sentence is now true somewhere other than in my head.

3. Prove the test can fail, or you have shipped a test that tests nothing

I did not believe the green run. I added a rule to the print stylesheet to deliberately break it:

@media print { .plan-table { min-width: 730px } }

That produced nine A4 overflow failures naming the table, with the Letter pass still clean — which is exactly the A4-only breakage the second paper was added to catch. Then I took the rule out.

This habit has earned its keep more than once. The same week, a different check in our gate was iterating (w.ids || []) over a data shape that had since grown a second form with no ids field. It looped zero times, passed, and reported a happy number. Ten entries were silently unverified for days. A check you have never watched fail is a check you have never tested.

While I am confessing: I spent weeks taking "390px phone screenshots" with --window-size=390,844, and Chrome on macOS refuses to make a window narrower than 500 CSS px, so every one of those was a 500px page cropped down. The site had never been rendered at phone width, and a hero image had been invisible on every phone since launch. Emulation.setDeviceMetricsOverride is the fix there too. If your mobile checks go through --window-size, go and load a page that prints its own innerWidth before you trust another one.

The takeaway

Grep your own product copy for numbers and promises — "two pages", "under a minute", "works offline", "fits on one screen". Each of those is an assertion you have published and are probably not testing. Printing is just the one where the user finds out at the printer, alone, with the thing half-done.
