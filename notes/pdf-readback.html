A 305-line PDF writer, and why I read every PDF it makes back out again

Engineering note · 26 November 2026 · 6 min read

Our printables are PDFs: weekly meal plans, grocery lists, a prep checklist. They come out of a PDF writer with no dependencies, about 300 lines of plain Node. That is less brave than it sounds. A PDF that uses only the fonts every reader already has is mostly text you can write with string concatenation.

This post isn't really about writing PDFs, though. It's about the decision that made the writer worth having: keep the output simple enough that a test can read it back, then turn "someone should skim the PDFs before release" into a check that fails the build.

1. The writer: base-14 fonts, one table of widths

PDF readers ship 14 standard fonts. If you use one of them (Helvetica, Helvetica-Bold and so on), you embed no font file at all. You declare it:

<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica-Bold /Encoding /WinAnsiEncoding >>

The catch is that nothing measures text for you, and you need measurements to wrap lines, centre headings and right-align prices. The fix is a table of advance widths for each printable ASCII character, in thousandths of an em, copied from the font's metrics file. Then a width is a sum:

function measure(str, fontName, size) {
  const f = fontOf(fontName);
  let total = 0;
  for (const ch of String(str)) {
    const c = ch.codePointAt(0);
    if (c >= 32 && c <= 126) total += f.widths[c - 32];
    else if (EXTRA[ch]) total += EXTRA[ch][f.key];
    else total += f.widths[0];
  }
  return (total / 1000) * size;
}

EXTRA is the other half: the handful of non-ASCII characters the copy uses, such as curly quotes, the em dash, ½ and °, each mapped to its WinAnsi byte and width. Any character outside that table is written as ?. Keep that in mind, because it comes back in section 3.

The rest is short. Callers get a top-left origin in points, because that's how people think about a page, and every y gets flipped once on the way out. Every page's drawing becomes one content stream: BT, a colour, /F2 14 Tf, a 1 0 0 1 x y Tm to place the line, (text) Tj, ET. At the end, objects are written in order, their byte offsets are recorded with Buffer.byteLength(out, 'latin1'), and the cross-reference table is built from those offsets. If any offset is wrong by one byte, some readers will quietly repair the file and others will refuse to open it, so measure in the same encoding you write in.

The 20-page kit comes out at 168 KB on Letter, with nothing compressed.

2. Not compressing is the feature

Real PDF libraries deflate their content streams, and so should you if file size matters. Ours doesn't, on purpose. Every line of text in every file is still sitting in the bytes as (Wednesday) Tj, right after the Tm that placed it and the Tf that set its font and size. So a checker can walk the stream with a few regular expressions and rebuild every text run with its exact position, font, size and width:

} else if ((mm = ln.match(/^1 0 0 1 ([\d.-]+) ([\d.-]+) Tm$/))) {
  x = parseFloat(mm[1]); yBase = parseFloat(mm[2]);
} else if ((mm = ln.match(/^\((.*)\) Tj$/))) {
  const text = decodePdfString(mm[1]);
  const w = measure(text, font, size) + tc * [...text].length;
  const top = pageH - yBase - size * 0.86;
  runs.push({ text, x, top, bottom: top + size * 1.02, right: x + w });
}

The checker uses the writer's own measure(), so the two can't disagree about how wide a word is. The page order comes from the /Kids array, not from object order, because those aren't guaranteed to match.

That gives 1,818 text runs across the four PDFs (free pack and paid kit, each on Letter and A4). Every run is checked for these:

  • Margins. Any run that starts left of the margin, ends past the right one, or drops below the footer rule.
  • Collisions. Any two runs whose boxes overlap. The design draws some headings twice, a pale offset copy under the coloured one, so identical text and near-white text are exempt. That exemption is written down in the code, with the reason.
  • Characters outside Latin-1 that made it into a run.

A visual review can't promise any of that across 52 pages and two paper sizes. A loop can.

3. The bug the read-back could not see, and where I check it instead

The writer turns any character it can't encode into a literal ?. Read the file back and a lost apostrophe looks exactly like a question the copy really asked. You can't tell them apart from the output.

So that check runs at the source instead. It scans the files the copy lives in for every non-ASCII character and fails if EXTRA doesn't cover it. The general lesson is that read-back testing has blind spots exactly where the writer's own fallbacks are, and those need a check somewhere else.

4. Text the data has but the page never shows

This is the one that hurt. The kit's data has always held a prep-ahead note for each of its 20 dinners. Those notes are where a night says, word for word, "Thaw the frozen chicken and rice in the fridge overnight." The code that draws the PDF never printed them at all. So the kit's prep day told the reader to freeze half the chicken for Friday, and nothing anywhere told them to thaw it. Every layout check passed, because text that was never drawn can't overflow a margin.

Once the text can be read back, the fix is cheap. For every record in the source data, assert that its text appears somewhere in the file's printed text:

for (const rot of ROTATIONS) for (const d of rot.dinners) {
  if (d.prep && !printed.includes(key(d.prep)))
    problems.push(`prep-ahead note for ${rot.name} ${d.day} is not printed anywhere`);
}

key() collapses whitespace and drops non-ASCII, so a line that wraps across two Tj runs still matches once the runs are joined. The same pattern now covers every step and rule of the method the free pack teaches.

5. Numbers in the copy are claims too

The copy used to spell out counts by hand: "five rules", "Four Starter Rotations", "Twenty printable pages". They were all true, and nothing checked them. Now each count is generated from the data, and the checker reads the printed sentence back and compares the number with the data, or with the file's own page count for "printable pages".

One rule made this hold up: a claim pattern that matches nowhere is a failure, not a pass. Otherwise the first rewording turns the check off without anyone noticing.

6. I found a gap in my own checker while writing this

Headings in the kit are letter-spaced. The writer emits 1.1 Tc before them and 0 Tc after. Until today, the read-back measured those runs without the extra spacing, so it saw every spaced heading narrower than it prints. Nothing was actually broken: the tightest spaced run, on A4, still clears the right margin by 8.8 points. But a longer heading could have printed past the margin with the check still green.

The fix is the tc * [...text].length term in the snippet above. Before trusting it, I multiplied every Tc by 40 in a throwaway copy. The checker went from PASS to 348 margin failures, which is the outcome you want. A check you haven't watched fail hasn't been tested yet.

The takeaway

You don't need a PDF library to make simple documents. The bigger point is the format choice: if you control a generator, keep its output plain enough to parse and test it from the reader's side. Check where every line landed, whether it collides with anything, and whether everything in your data actually reached the page. A one-time visual skim only tells you about the one version you looked at.
